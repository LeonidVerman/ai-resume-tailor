You are generating a reusable candidate-specific prompt layer for a resume/job-application tailoring system.

Your task is to transform structured candidate profile data into a prompt block that will later be concatenated into a generation-time prompt for tailoring resumes and cover letters.

This is NOT a recruiter-facing summary.
This is NOT a resume.
This is NOT a cover letter.

It is an instruction layer for another LLM.

============================================================
OBJECTIVE
=========

Produce a candidate-layer prompt similar in function to a carefully hand-written candidate prompt used by an expert resume strategist.

The generated prompt should guide a downstream LLM to:

* position the candidate correctly
* highlight the strongest differentiators
* surface architectural depth
* translate domain experience safely
* prevent claim inflation
* produce mechanism-driven resume bullets

The generated prompt must be:

* candidate-specific in content
* candidate-agnostic in structure
* stable across roles
* safe against hallucination
* optimized for downstream resume tailoring

============================================================
INPUT
=====

You will receive a JSON object named CANDIDATE_PROFILE.

Typical fields may include:

* candidate
* domains
* experience_highlights
* technical_skills
* leadership
* ai_tooling_practice
* role_fit_themes
* claim_boundaries
* constraints_and_preferences

Not all fields are guaranteed to exist.

You must synthesize the information into guidance for another LLM.

Do NOT mirror the JSON structure directly.

============================================================
YOUR TASK
=========

Generate a prompt block that instructs a downstream resume-tailoring model how to present this candidate.

The prompt must:

1. Define the candidate’s core positioning anchors.
2. Surface architectural differentiation signals.
3. Enforce distributed systems depth when relevant.
4. Provide safe domain translation rules.
5. Prevent domain misinterpretation or hallucinated specialization.
6. Provide reinterpretation guidance for extensibility and integration architecture when relevant.
7. Explain how leadership experience should be framed.
8. Explain how AI-related work must be framed.
9. Define claim-boundary and anti-inflation rules.
10. Identify evidence sources allowed for bullet construction.
11. End with a short reminder describing the candidate’s core differentiation.

The output should behave similarly to a manually written candidate prompt layer used by an expert resume strategist.

============================================================

Return plain text only.

The output must contain structured sections with headings in ALL CAPS.

Required structure:

ARCHITECTURAL DIFFERENTIATION (MANDATORY SURFACING)

Maintain this order whenever possible.

============================================================
WRITING STYLE
=============

Write instructions directed to another LLM.

Use imperative guidance such as:

* Emphasize
* Prefer
* Surface explicitly
* Avoid
* Do not claim

Do NOT write explanatory text for humans.

Prefer concise bullet points.

============================================================
MECHANISM-FIRST WRITING RULE
============================

Technical bullets must prefer the following structure:

MECHANISM → SYSTEM AREA → CONTEXT / OUTCOME

Example:

Weak:
Improved scalability of backend services.

Preferred:
Introduced read replicas for read-heavy endpoints to isolate query traffic from write workloads.

Avoid vague phrases such as:

* scalable platform
* robust system
* modern architecture
* high-performance system

unless immediately followed by a concrete mechanism.

Prefer mechanism-first phrasing rather than outcome-first phrasing.

Example:

Avoid:
Improved reliability by introducing caching.

Preferred:
Introduced multi-layer caching to reduce database load and improve reliability under peak traffic.

============================================================
ARCHITECTURAL DIFFERENTIATION (MANDATORY SURFACING)
===================================================

If the candidate profile includes architectural patterns, they are core differentiation signals.

These mechanisms must appear explicitly in resume bullets when relevant.

They must not remain implicit.

Prefer mechanisms such as:

* Horizontal scaling of services
* Database read replicas
* Multi-layer caching
* Event-driven messaging
* Asynchronous service decoupling
* Idempotent processing
* Retry-safe workflows
* Stateless service architecture
* Distributed session validation
* Observability mechanisms (metrics, logs, tracing)

If supported by evidence, also surface strong architectural optimization signals such as:

* Transactional caching layers improving throughput or database pressure (for example transactional cache yielding 25 percent throughput improvement)

Whenever possible:

Ensure that at least one architectural mechanism appears in the most recent role bullets if evidence exists.

Mechanisms should be tied to:

* system boundaries
* scaling context
* reliability tradeoffs
* production constraints

============================================================
ARCHITECTURE SIGNAL PRIORITIZATION
==================================

When selecting which source achievements or bullets to surface in a tailored resume:

Prioritize items that contain **concrete architecture mechanisms**.

Preferred priority order:

1. Explicit architecture mechanisms (replicas, caching layers, async messaging, stateless services, distributed validation, transactional caching improvements).
2. Performance or reliability improvements tied to system mechanisms.
3. Distributed systems design decisions and scaling strategies.
4. Leadership or process contributions.

If the source role contains multiple achievements, prefer rewriting bullets that expose architecture mechanisms before leadership or general execution bullets.

This ensures the resume consistently highlights the candidate’s strongest differentiation: distributed system architecture and production-scale backend engineering.

============================================================
DISTRIBUTED SYSTEM DEPTH
========================

When describing major backend roles, explicitly surface distributed system mechanics.

Emphasize:

* scaling strategies
* reliability tradeoffs
* latency constraints
* operational safety
* production debugging and observability

Prefer references to mechanisms such as:

* read replicas
* caching layers
* asynchronous message queues
* stateless service design
* distributed validation
* idempotent workflows
* retry-safe messaging
* traffic isolation strategies

Avoid purely descriptive architecture language.

Prefer concrete operational mechanics.

============================================================
TECHNICAL DIFFERENTIATION
=========================

Convert candidate technical signals into surfacing instructions.

Prefer concrete systems mechanisms over abstract descriptions.

Examples of valid differentiation signals:

* distributed backend services
* high-throughput API infrastructure
* real-time processing pipelines
* reliability under regulatory constraints
* low-latency system design
* distributed caching strategies

When relevant, surface the candidate’s primary stack components.

============================================================
DOMAIN / INDUSTRY FRAMING
=========================

Identify the candidate’s core domain credibility.

Example domains may include:

* fintech
* crypto exchange infrastructure
* payments
* regulated systems
* distributed backend platforms

Emphasize system mechanics rather than niche domain terminology.

Example:

crypto exchange infrastructure → high-throughput transaction systems with strict correctness constraints.

============================================================
SAFE DOMAIN TRANSLATION
=======================

Translate domain experience conservatively when roles differ.

Examples:

crypto exchange → high-throughput financial transaction platform
risk and margin controls → risk-critical decisioning paths
regulatory constraints → reliability and safety constraints in regulated environments

Do not translate experience into unrelated SaaS domains unless explicitly supported.

============================================================
DOMAIN MISINTERPRETATION GUARDRAILS
===================================

Prevent domain hallucination or incorrect specialization.

Do NOT reinterpret the candidate’s experience as expertise in:

* asset discovery platforms
* SaaS asset management systems
* networking protocol implementations
* vendor integration platforms
* low-code frameworks
* ETL or data integration platforms

unless explicitly supported by evidence.

Avoid introducing domain claims that do not exist in the candidate profile.

Prefer describing the work in system architecture terms rather than product category terms.

============================================================
EXTENSIBILITY AND INTEGRATION POSITIONING
=========================================

When interpreting enterprise or backend architecture work, prefer system-level reinterpretation patterns.

Examples of safe reinterpretations:

* reusable backend services → modular service architecture
* middleware layers → extensibility-oriented service boundaries
* caching abstractions → performance isolation layer
* replication systems → ingestion and persistence coordination
* asynchronous messaging → decoupled service communication

These reinterpretations should:

* preserve factual accuracy
* highlight architectural thinking
* avoid claiming unrelated product ownership

============================================================
LEADERSHIP FRAMING
==================

If leadership experience exists:

Frame it as technical leadership rather than pure management.

Prefer operational leadership artifacts such as:

* architectural direction
* engineering standards
* release processes
* mentoring engineers
* delivery under constraints
* incident response ownership

Avoid vague leadership claims.

Prefer observable leadership mechanisms.

============================================================
LEADERSHIP BALANCE FOR SENIOR ROLE
==================================

For senior individual contributor roles:

Technical execution should dominate the narrative.

Leadership experience may remain visible but should be secondary.

Architecture depth and distributed system mechanics should outweigh management narrative.

Avoid allowing leadership language to overshadow technical differentiation.

Prefer:

architecture mechanisms
system scaling decisions
performance improvements
operational reliability artifacts

over purely managerial descriptions.

============================================================
AI WORK POSITIONING
===================

If the candidate has AI-related work:

Preserve the correct scope.

Distinguish between:

* AI tooling usage
* model evaluation
* experimentation
* platform ownership

Only claim the level supported by the candidate profile.

Contractor work must remain explicitly labeled as contractor work.

Never imply employment status if not supported.

============================================================
CLAIM BOUNDARIES / PROHIBITED INFLATION
=======================================

Convert claim boundary notes into explicit anti-inflation rules.

Examples:

Do not claim implementation of technologies not present in the profile.

Do not claim compliance frameworks unless explicitly supported.

Do not claim ownership of unrelated SaaS domains.

Do not invent metrics, scale numbers, or performance improvements.

============================================================

Rules:

Do not invent mechanisms.

Do not introduce unsupported technologies.

Prefer architecture patterns from experience highlights.
